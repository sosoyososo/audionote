# ADR-0010: 标签语义归并 —— 模型只提建议，用户拍板

| Field | Value |
|---|---|
| **Status** | ACCEPTED (2026-10-29) |
| **Date** | 2026-10-29 |
| **Related** | ADR-0002（`optimizeAndProcess` 的四字段 schema）、ADR-0003（多 provider 与 prompt 冻结）、ADR-0008（provider profiles 在数据文件夹）、`docs/superpowers/specs/2026-10-26-tag-vocabulary-maintenance-design.md` §3 方向 B |
| **Supersedes** | — |

## 1. 决定

**模型只提建议，合并由用户执行。**

「智能合并标签」在标签列表页上做一次 LLM 调用，大模型给出**哪些标签语义相同、可以并成一个**的建议清单。清单交给用户：每条建议可以**删掉**（不认同）、可以**取消勾选**（这一条先不合）、**合并后的名字可以改**。**只有用户点了「合并 N 组」，合并才会发生** ✓。

模型永远不自己改标签表 ✓。

## 2. 为什么

标签合并是**破坏性**的：它要改写历史记录上的标签 ✓。一个把 158 个标签收敛成 40 个的自动归并，如果模型判断错了几个，用户不会知道错在哪 ✓ —— 因为他没参与 ✓。

这与仓库里已有的原则一致 ✓：`MergeTagsView` 的两段式确认 ✓、ADR-0007 的「读不出来不等于空库」✓、ADR-0005 的「更新不能删掉调用方没重申的字段」✓ —— 一句话：**破坏性的事不自动发生** ✓。

另外，**建议的价值全在人当场决定** ✓。没人盯着的时候提出二十组建议，等于白花一次 LLM 调用 ✓ —— 所以这个功能是**用户手动触发**的 ✓，不做后台扫描 ✓。

## 3. 新的 LLM 调用

`LLMService.proposeTagMerges(tags:profile:apiKey:)` ✓，**独立于现有两次调用** ✓：

| 调用 | 干什么 | schema |
|---|---|---|
| `optimizeAndProcess` | 优化一条笔记、抽标题摘要标签 | ADR-0002 冻结 ✓ |
| `findRelated` | 找相关笔记 | 自己的格式 ✓ |
| `proposeTagMerges` | **给词表分组** | 自己的格式 ✓（本 ADR 冻结 ✓） |

三种任务塞进一个 prompt，模型就会去答错的问题 ✓ —— 所以是三次调用 ✓。

响应格式 ✓：

```json
{"merges": [{"target": "工作", "sources": ["工作项", "工作会议"]}]}
```

**这个调用有多慢（2026-10-29 真机实测 ✓）**：这个 prompt 会让模型**把思考写在正文里** ✓（MiniMax-M3 的 `<think>` 块 ✓），一次实测的回答有 **29,813 个字符** ✓ —— 而真正的 JSON 答案只有几百字符 ✓✓。所以：

- **超时放宽到 240 秒 ✓**，重试 2 次 ✓ —— 实测生成要 **89 秒** ✓，而超时当时是 **90 秒** ✓ —— **每次都差一点超时** ✓，于是每次点击都变成「两次请求 + 约三分钟」 ✓✓。超时必须**明显高于**生成时间 ✓，重试只是保险 ✓，不是常规路径 ✓
- **答案的规模要限制** ✓ —— 最多 10 组 ✓、每组最多 4 个来源 ✓、**合并后的名字必须出现在 2 条及以上笔记里** ✓（来源可以只出现一次 ✓，所以「工作项 → 工作」这种关键合并依然成立 ✓）
- **流式曾经做过，又回退了** ✓（2026-10-29 ✓）：流式能把超时从「整个回答」变成「两个 chunk 之间」✓✓，也能让用户看着模型在想什么 ✓，但这条路径的复杂度没有被认可 ✓，于是整体回退 ✓（提交 `6e47506` 与它的回退 ✓）。**这是个已知的取舍**：这个调用**可能慢、也可能超时** ✓，超时时界面会提示重试 ✓。

**解析必须容错** ✓：一条格式不对的建议丢掉，其余的照常 ✓；整个信封读不出来才报错 ✓。

**模型说的标签名要核对** ✓：

- **目标必须是库里已有的标签** ✓ —— 合并不创造新词 ✓
- **来源必须是库里已有的标签** ✓ —— 模型不许编 ✓
- **按 identity 核对** ✓（`TagIdentity.key` ✓）—— `Work` 和 `work` 是同一个标签 ✓，不能当成两个 ✓

## 4. 不存归并映射

合并落地之后，**记录上的标签本身就是映射** ✓：所有带 `工作项` 的记录都变成了 `工作` ✓，`工作项` 从库里消失 ✓。

**因此不存同义词词典** ✓。存一份就多一样会变旧的东西 ✓ —— 而它唯一的用处（让模型以后优先用 `工作` 而不是 `工作项` ✓）已经被方向 A 接管了 ✓：词表里没有 `工作项` 了 ✓，模型也就没有它可以复用 ✓✓。

## 5. 一次写盘

一次合并 = 整库记录的读 + 写 ✓。**一批建议一次写** ✓，不是一组一次 ✓ —— 三十组逐个应用就是三十次全库重写 ✓。

落盘路径复用现有的 `TagMerger.merge` ✓（它是纯函数 ✓），写盘走 `TranscriptionStorage` ✓。

## 6. 重叠的建议要跳过

模型可能同时给出 `[A, B]` 和 `[B, C]` ✓。**后一组如果用到了已被前一组吃掉的标签，整组跳过** ✓，并把跳过的条数**如实报给用户** ✓ —— 不是静默丢弃 ✓。

不跳过的话，两条互相矛盾的建议会叠成一条用户从没同意过的合并链 ✓。

同样被跳过的还有：**改了等于没改**的组 ✓ —— 重写文件产出一个一模一样的文件不值得 ✓。

## 7. 后果

- 用户在标签列表页多了一个入口 ✓，点它要花一次 LLM 调用 ✓
- 合并**不可撤销** ✓ —— 靠**预览 + 逐条确认**来控制，不靠撤销 ✓
- 合并之后 `availableTags` 的计数、chip 排序、筛选口径、三个数（GLOSSARY 的「the three library counts」✓）必须重新对得上 ✓ —— 合并后自动重载 ✓
- **库读不出来时，合并必须拒绝执行并说明原因** ✓ —— 不能把它当成「没什么可合并」而静默地什么都不做 ✓✓。这正是 ADR-0007 对写入者的要求 ✓（「读不出来的库不能当成空库 ✓，对写入者也一样 ✓」），而合并就是写入者 ✓。存储层把「够不着文件夹」折叠成了「没有文件」✓，所以合并这一层必须自己查协调器的状态 ✓✓
