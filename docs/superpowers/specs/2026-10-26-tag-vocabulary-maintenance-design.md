## 1. 问题

2026-10-26 的实况：**43 条笔记，158 个标签**。

158 个标签摊到 43 条笔记上，意味着每条笔记平均挂着三四个标签，而**绝大多数标签只出现过一次**。也就是说，标签已经不再是「分类」，退化成「这条笔记的关键词」——每条笔记都自带一套只属于它自己的词。

后果是连锁的：

- **筛选失去意义**：筛一个只出现过的标签 = 筛出一条笔记，筛不出「这一类东西」✓
- **chip 行滚不到头**：158 个 chip 横向排开，滚到最后要滑很久，而滑过去的那个大概率你不会用 ✓
- **计数和排序失效**：chip 上的数字几乎全是 1，按次数排序和按字母排序没有区别 ✓
- **合并功能救不了场**：手动合并一次处理两个标签，158 个标签要人来收敛 ✓

## 2. 现状：已经有什么，缺什么

### 2.1 已有：手动合并

`TagMerger` + `MergeTagsView`（见 `2026-10-17-tag-merge-design.md`）：用户挑两个或多个标签，合成一个，两段式确认。

它不够的原因不是不好用，是**它的工作方式**：

1. **手动**：收敛 158 个标签要人来一个个挑 ✓
2. **不判断语义**：点哪两个就是哪两个，等价性靠人眼 ✓
3. **只作用于当下**：合并完，新抽出来的标签还是新的，长尾继续长 ✓

### 2.2 方向 A 已经有雏形了，而且有一个反向的截断

Prompt 里**早就有**【已有标签】块（`LLMService.swift:225`）：「如果上面已有能准确概括本条的标签，直接复用它的写法；只有在确实没有合适的已有标签时，才新造一个新标签」✓

词表由 `TranscriptionViewModel.existingTagVocabulary`（`:1042`）组装：全库标签按**出现频次**排序后取前 N 个喂进去 ✓

**而 N = 30**（`LLMService.swift:246` 的 `maxTagVocabulary`）✓

**先说清楚这个上限本身不是 bug**：它的注释写明了理由——「词表会和转写文本抢模型的注意力，所以要短，并且按库里真正用得多的排，头部才是复用最划算的地方」✓。所以「把 158 个标签全塞进去」是错的方向 ✓：**列表越长，模型越容易随手抓一个不相关的旧标签** ✓。

**真正的毛病在「按频次排序」这个选择方式**，它有一个自我实现的闭环：

- 膨胀长在**长尾**——只出现一两次的那些标签 ✓
- 词表按频次取前 30，等于**每次都把长尾挡在门外** ✓
- 于是：一条讲长尾话题的新笔记，模型手上没有任何可复用的词 → 只能再造一个 → 这个新标签还是长尾 → **它也永远进不了词表** ✓✓
- **一个只用过一次的标签，因为没被给过，所以永远不会有第二次** ✓

这是「明明已经有提示了，标签还是涨到 158」的一条机制性解释。**它是不是全部原因，需要用数据确认**（见 §5 ✓）。

**修法不是把列表拉长，是换选择方式**：**和本条内容相关的标签优先**，频次只用来在「相关的」内部排序和补位 ✓。这样长尾里那些**恰好对得上本条**的词有了机会，而列表还是短的 ✓（注意力的顾虑依然成立 ✓）。

**2026-10-29：方向 A 的第一轮已经实现** ✓（`TagVocabularySelector` ✓，实现计划见 `docs/superpowers/plans/2026-10-29-tag-vocabulary-direction-a-plan.md` ✓）：选择方式换掉了 ✓，上限仍是 30 ✓（理由未变 ✓），并加了埋点 ✓——下一次真机录音就能拿到「模型返回的标签里，有几个是词表给过的」这个数 ✓（§5 的验证项 ✓）。

## 3. 方向（两条，互补，缺一不可）

### 方向 A —— 源头抑制：抽标签时优先复用已有的标签

**做法**：抽标签的时候，**提前把本地已有的标签带上**，让模型优先从已有的标签里挑；只有在确实没有能用的已有标签时，才创建新的标签。目的是**避免同一个标签被反复创建**——同一个意思换个说法又长出一根（`工作` / `工作项` / `工作会议` ✓），长尾就是这么长出来的。

（已有雏形，见 §2.2：**提示词里已有【已有标签】块** ✓。要解决的是「给哪些、给多少、怎么排」✓ —— 现状的 30 个上限把长尾挡在门外 ✓。）

### 方向 B —— 存量收敛：在标签列表页做「智能合并标签」

**入口**：标签列表页 —— 就是那个列着全部 158 个标签的页面（`TagPickerSheet` ✓）。在这里新增一个操作：**智能合并标签** ✓。

**流程**：

1. 用户点「智能合并标签」✓
2. **大模型判断哪些标签语义相同、可以合并**，返回一份**合并建议清单** ✓（每条建议：一组该合并的标签 + 合并后的名字 ✓）
3. **不是一键合并** ✓：点开之后看到的是**建议**，不是已经改了 ✓
4. 用户可以**全部同意** ✓，也可以**把其中一些删掉、只同意剩下的** ✓
5. **必须用户明确允许，最终的合并才会执行** ✓ —— 模型只负责提建议，落地由用户拍板 ✓

（这条与现有 `MergeTagsView` 的两段式确认是同一个原则：破坏性的操作不自动发生 ✓。）

两条是互补的，不是二选一：

- 只做 A：存量那 158 个还在，而且 A 只对**之后**的笔记有效 ✓
- 只做 B：新的还在源源不断地产生，扫完一轮又长一轮 ✓

## 4. 目标

1. 标签表回到「少数几个被反复复用的分类词」的量级。**先量出度量再定数字**，不预设目标值 ✓
2. 同一语义的标签不再并存 ✓
3. 「优先复用已有标签」成为**结果**而不只是提示——新抽出的标签绝大多数来自已有词表 ✓
4. 归并是破坏性的（要改写历史记录上的标签），所以**模型只到「建议」为止，落地合并必须由用户明确允许** ✓：建议清单可以整体同意，也可以逐条删改后再同意 ✓。与现有 `MergeTagsView` 的两段式确认是同一个原则 ✓

### 度量（先有尺子，再谈达标 ✓）

- 标签数 / 笔记数 的比值 ✓
- 「只出现一次的标签」的数量 ✓
- 新抽出的标签中，复用已有标签的比例 ✓

## 5. 待回答的问题（下次动手前要先答 ✓）

**方向 A**

- 词表给多少个？按频次截断（现状）还是按语义覆盖（罕见但通用的词优先）？还是分批给？
- 模型不听话时怎么办——提示是软的。要不要在**结果侧**做一次归一化（把模型返回的标签映射回词表）？
- 冷启动（词表为空）时的行为 ✓（现状：词表为空时 prompt 与没有词表时逐字节相同 ✓）

**方向 B**

- 什么时候跑？一次全量扫描，还是增量（每加一个标签就和存量比）？
- 归并映射存哪？`TagIdentity` 是「同一个标签」的唯一权威（大小写 / 空白 ✓）——语义归并的映射是它的邻居，还是并进它？
- 归并后怎么重写历史记录上的标签？和 ADR-0005 的「更新不能删掉调用方没重申的字段」怎么协调？
- 词表本身要不要变成**一等公民**（像 `profiles.json` 那样，ADR-0008 的思路 ✓）？

**已经定了的（2026-10-29，用户拍板 ✓）**

- 方向 B 的交互：模型给**建议清单**，用户**全盘同意或删减后同意**，**没有一键合并** ✓，最终合并**必须用户允许** ✓（§3 ✓）

**验证现状**

- §2.2 说的「长尾被挡在门外」，是不是 158 这个数字的主要来源？要拿数据确认（词表里没出现过的标签占多少、这些标签后来有没有被复用）✓

**已经测到的（2026-10-29，真机 iPhone Air / iOS 26.3 ✓）**

方向 A 第一轮上线后，在真机上做了两次带 LLM 优化的处理 ✓，每次打两行日志 ✓：

| | 第一次 | 第二次 |
|---|---|---|
| 词表大小 | 30 ✓ | 30 ✓ |
| 模型返回的标签数 | 5 ✓ | 4 ✓ |
| **返回的标签里，词表给过的** | **5 / 5** ✓ | **4 / 4** ✓ |
| 相关规则换进来的标签（旧口径没有的） | 未记录 ✓ | `相关度计算` ✓ |

**第三次（决定性的一次 ✓）**：一条讲「相关度计算」的笔记 ✓

```
vocabulary selection: legacy=30 relevant=30 broughtIn=["相关度计算", "语音测试"]
tag vocabulary: offered=30 returned=4 reused=4 tags=相关度计算,笔记相关度,测试验证,功能测试
```

**「相关度计算」出现在 `broughtIn` 里，说明旧口径选不中它 ✓；它出现在模型返回的标签里，说明模型复用了它 ✓。** 因果链因此闭合 ✓：

> 旧口径下，这个标签模型**根本看不到** ✓ → 模型只会另造一个（`相关度` / `相关度逻辑` ✓）→ **那正是膨胀的机制本身** ✓。新口径下它被复用 ✓ ✓。

**这三次测量说明的** ✓：

- **模型确实在复用给它的词表** ✓ —— 5/5、4/4、4/4 ✓ 全是 100% ✓，管道是通的 ✓，§2.2 里「提示存在但没用上」那一类问题**不在这里** ✓
- **相关规则确实在起作用** ✓ —— 它把旧口径选不中的冷门标签送了进去 ✓，而模型用上了 ✓✓
- **方向 B 的活是实打实的** ✓ —— 第三条笔记上，模型同时给出了「相关度计算」**和**「笔记相关度」✓：**同一条笔记上出现了两个语义重复的标签** ✓✓。这不是假设，是现场发生的 ✓ —— 「智能合并」要解决的正是这个 ✓

**顺带记一条教训** ✓：真机看日志必须**挂控制台启动**（`devicectl device process launch --console` ✓），而且 App 已经在跑时 devicectl 会拒绝再启一个实例 ✓（要先 terminate ✓）—— 更要命的是，**控制台挂上之前打的日志全丢了** ✓（今天就丢过一次 ✓：那次词表测量不得不重做一遍 ✓）。`.remember` 里早有这条债 ✓：**`Logger.swift` → `os.Logger`** ✓。

**2026-10-29：这条债还了** ✓ —— `Logger` 现在同时写**两个出口** ✓：stdout ✓（给命令行实时看 ✓）和**统一日志** ✓（给事后查 ✓，Xcode / Console.app 都能读 ✓，而且**留得住** ✓）。顺带查清一件事实 ✓：**Mac 的 `log show` / `log stream` 只能读 Mac 自己的日志** ✓，`log collect --device-udid` **要 root** ✓ —— 所以从命令行盯一台设备，只有「启动时挂控制台」这一条路 ✓。

## 6. 动手时必须遵守的约束

- `TagIdentity` 是「同一个标签」的唯一权威（大小写折叠、空白折叠 ✓）。语义归并**不能绕过它**另起一套身份判定 ✓
- API key 永远不进文件夹（ADR-0008 ✓）。归并走 LLM 时同样 ✓
- 任何在线调用前先过 `NetworkMonitor.shared.checkConnectivity()` ✓
- 在线调用走现有的 provider profile（ADR-0003 ✓），不新增第二套 LLM 通道 ✓
- 破坏性操作（改写历史记录的标签）必须可撤销或至少可确认 ✓
- **模型只提建议，不执行合并** ✓ —— 「智能合并」的结果必须先变成一份用户看得见、可以逐条否决的清单 ✓（§3 方向 B ✓）
- 合并后 `availableTags` 的计数、chip 排序、筛选口径必须重新对得上——这三个数字刚刚才被理顺（见 GLOSSARY 的「the three library counts」✓）

## 7. 一句话

> 标签膨胀不是「合并功能不够用」，是**抽取时没有词表约束**（方向 A）+ **存量没有语义归并**（方向 B）两件事叠加。
> 手动合并能收拾眼前的，收拾不了机制。

## 8. 顺序、边界与验收

### 8.1 顺序：A → B

**先 A，后 B** ✓ —— 不是因为 A 更重要，而是因为**两件事的作用对象不同**：

| | 管的是 | 不做会怎样 |
|---|---|---|
| A | **以后**抽出来的标签 | B 清完 158 个，下一条笔记又长出新词 ✓ |
| B | **已经存在**的 158 个 | A 只对以后的笔记有效 ✓，存量原地不动 ✓ |

只做 B：B 的成果被 A 的缺失吃掉 ✓。只做 A：存量那 158 个继续躺在那 ✓，而且它们大部分是**词表提示出现之前**（2026-10-17 ✓）就攒下的 ✓。

**但实现顺序上，A 更便宜** ✓：A 的管道已经通了 ✓（词表 → prompt ✓），要改的只是「给哪些」✓；B 还差一次新的 LLM 调用 + 一套建议清单 UI ✓。所以**先 A，用 A 的运行结果去定 B 的设计** ✓（比如 B 到底要扫多少标签、语义等价到什么程度才算 ✓）。

### 8.2 边界：这一轮不做什么

**方向 A 的第一轮只做三件事** ✓（实现计划见 `docs/superpowers/plans/2026-10-29-tag-vocabulary-direction-a-plan.md` ✓）：

1. **埋点** ✓ —— 先量清楚「模型返回的标签里，有几个是词表给过的」✓（没有基线，改了也说不清有没有用 ✓）
2. **换选择方式** ✓ —— 相关优先、频次补位 ✓（§2.2 ✓）
3. **测试** ✓

**明确不做** ✓：

- **不动 prompt 的措辞** ✓ —— ADR-0003 冻结了它 ✓；这一轮改的只是「哪些标签进这个词表」✓
- **不做结果侧归一化** ✓ —— 把模型返回的标签映射回词表 ✓，那是「语义等价」的问题 ✓，属于 B ✓（`TagIdentity` 已经在读的时候处理大小写和空白了 ✓）
- **不把词表变成一等公民** ✓（像 `profiles.json` 那样 ✓）—— 那是第三个话题 ✓
- **方向 B 的全部** ✓ —— 新 LLM 调用、建议清单 UI、归并映射的存放 ✓，等 A 的数据出来再设计 ✓

### 8.3 验收标准

**方向 A**（一轮之后要能回答）✓：

1. 「模型返回的标签里，有几个是词表给过的」这个数字**能被记下来** ✓（埋点 ✓）
2. 有基线才能比 ✓：改动前后各记一次 ✓
3. 相关的标签**能挤掉**不相关的高频标签 ✓（选择器的测试要盖住这一条 ✓）

**方向 B**（等它做完）✓：

1. 158 个标签收敛到「少数几个被反复复用的分类词」的量级 ✓（度量在 §4 ✓）
2. 「只出现一次的标签」数量下降 ✓
3. **没有任何一次合并是用户没允许就发生的** ✓（§3 方向 B ✓）

**整体**：

- 合并之后 `availableTags` 的计数、chip 排序、筛选口径、三个数（见 GLOSSARY ✓）必须重新对得上 ✓
